# Security policy

Applies to every repository in the Morgenruf organisation.

## Reporting a vulnerability

Please do not open a public issue for a security problem.

Report it through
[GitHub private vulnerability reporting](https://github.com/morgenruf/morgenruf/security/advisories/new),
or by email to **security@morgenruf.dev**.

Include what you need to make the problem reproducible: the version or commit, the
affected endpoint or component, and the steps. A proof of concept helps but is not
required to report.

You will get an acknowledgement within three working days. Morgenruf is maintained by
a small team, so a fix may take longer than that, and you will get an honest estimate
rather than silence.

## Supported versions

Fixes land on the latest release. Older versions are not patched separately, so
upgrading is the supported path.

## Self-hosting: the things that actually matter

Morgenruf runs on your infrastructure, which means some of the security surface is
yours. These are the ones worth checking.

**Set `FLASK_SECRET_KEY` to a real random value.** It signs dashboard login tokens
and the Slack OAuth state parameter. Generate it with `openssl rand -hex 32`. Leaving
it unset makes login tokens unable to survive a restart and logs a warning; it must
never be set to a shared or guessable value.

**Keep the bot token in a secret, not a config map.** The Helm chart expects it in a
Kubernetes secret. It grants the app the ability to read channels and DM everyone in
your workspace.

**Put the app behind TLS.** Slack requires HTTPS for its request URLs, and the
dashboard session cookie should never travel in clear text.

**Restrict outbound requests if you can.** Webhooks and automation rules make the
server issue HTTP requests to URLs your admins supply. Morgenruf validates them
against loopback and private ranges, but a hostname that resolves to an internal
address will still pass. Egress rules are the reliable control.

**Rotate the webhook signing secret if it leaks.** Every delivery is signed with
HMAC-SHA256 over the raw body. Receivers should verify it with a constant-time
comparison against the bytes as received, not a re-serialised copy.

## Scope

In scope: the bot, the dashboard, the MCP server, the Helm chart, and the deployment
templates in `aws-deploy`.

Out of scope: findings that require an already-compromised Slack workspace or
Kubernetes cluster, vulnerabilities in Slack itself, and reports generated by a
scanner without a demonstrated impact on a real deployment.
